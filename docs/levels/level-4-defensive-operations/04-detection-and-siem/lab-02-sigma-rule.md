# LAB-404-02 · Write, Convert and Test a Detection

## Scenario and background

An SSH brute-force rule is the "hello world" of detection engineering, which is why it is usually written badly: a
threshold with no justified value, no negative case, and no test.

You will write it properly — hypothesis first, Sigma rule as the reviewable specification, native Wazuh
implementation, and four recorded tests. Then you will break it deliberately by changing the threshold and observe
what the tests catch.

## Learning objectives

1. Write a detection hypothesis with an explicit negative case before writing YAML.
2. Produce a Sigma rule that passes `sigma check`, and convert it to a supported backend to see what portability means.
3. Implement the same logic natively in Wazuh, mapping Sigma fields to decoded fields.
4. Validate the rule with `wazuh-logtest` before generating traffic.
5. Run positive, negative, no-data and regression tests, and record outcomes honestly.
6. Explain the semantic difference between Sigma's `count() by` and Wazuh's `frequency`/`timeframe`.

## Threat model

A remote attacker with a credential list attempts SSH authentication against an exposed host and succeeds. The
detection targets the *sequence*: many failures, then success. The lab's controlled activity reproduces the log
evidence without any real authentication attempts.

## Prerequisites check

From LAB-404-01: `lab-siem` running, `lab-ubuntu` active, `/var/log/lab404/auth-test.log` monitored, and the rule ID
that matched your synthetic failure line recorded. If you skipped that, `wazuh-logtest` is how you find it now.

## Procedure

### 1. Write the hypothesis first

Create `detections/README.md`:

```markdown
## DET-001 — SSH authentication failure burst

**Hypothesis:** If an attacker tries many passwords against SSH, then sshd logs on a monitored host will contain more
than five "Failed password" lines from one source address within two minutes.

**Negative case:** A user who mistypes a password twice and then succeeds will not reach the threshold.

**Data source:** /var/log/lab404/auth-test.log via the Wazuh agent (syslog decoder).

**Known limits:** does not cover key-based authentication failures the same way; does not see attacks against hosts
without an agent; a slow attack (one attempt per five minutes) stays below the threshold.
```

If you cannot fill in the negative case, stop — the rule is not ready to write.

### 2. Write the Sigma rule

`detections/rules/linux/ssh_auth_failure_burst.yml`:

```yaml
title: SSH Authentication Failure Burst
id: 3b7e5c1a-9d24-4f6b-8a10-6c2f4e9d7b31
status: experimental
description: More than five SSH authentication failures from one source in two minutes.
references:
  - https://attack.mitre.org/techniques/T1110/
author: CYB-404 lab
date: 2026/10/29
logsource:
  product: linux
  service: sshd
detection:
  selection:
    message|contains: 'Failed password'
  timeframe: 2m
  condition: selection | count(src_ip) by src_ip > 5
fields:
  - src_ip
  - user
falsepositives:
  - A user with a stale saved password retrying in a loop
  - An authorized vulnerability scanner using a default credential list
level: high
tags:
  - attack.credential_access
  - attack.t1110
```

Validate it:

```bash
python3 -m venv ~/sigma-venv && source ~/sigma-venv/bin/activate
pip install sigma-cli
sigma check detections/rules/linux/ssh_auth_failure_burst.yml
```

**Expected:** `Validation passed` or no errors. Warnings about unspecified fields are acceptable; an invalid
`condition` is not.

### 3. Convert to a supported backend

```bash
sigma plugin list | head -20
sigma plugin install splunk          # if not already present
sigma convert -t splunk detections/rules/linux/ssh_auth_failure_burst.yml
```

**Expected:** a Splunk search using `count by src_ip`. Save it as `detections/converted/splunk.txt`.

Now try the target you actually use:

```bash
sigma plugin list | grep -i wazuh || echo "no official Wazuh backend"
```

**Expected:** no official Wazuh backend. Record that in the README with the date. This is not a tooling failure — it
is the reason the next step is manual, and why the Sigma rule must remain the reviewable specification.

**What conversion does and does not prove:** it proves your logic is expressible in a backend's query language. It does
not prove the backend has the data or the field names. That is why the next step exists.

### 4. Implement it natively in Wazuh

On `lab-siem`, edit `/var/ossec/etc/rules/local_rules.xml` **inside the manager container** (or in the bind-mounted
config directory your compose file uses — check `docker-compose.yml` first):

```bash
docker compose exec wazuh.manager bash
vi /var/ossec/etc/rules/local_rules.xml
```

Add:

```xml
<group name="lab404,sshd,">
  <rule id="100420" level="10" frequency="6" timeframe="120">
    <if_matched_sid>5710</if_matched_sid>
    <same_source_ip />
    <description>LAB404: SSH authentication failure burst from a single source</description>
    <mitre>
      <id>T1110</id>
    </mitre>
  </rule>
</group>
```

**Change `5710` to the SID your failure line actually matched in LAB-404-01.** Wazuh base-rule numbering varies by
message ("invalid user" and "failed password for valid user" are different rules). A composite rule referencing a
SID that never fires will never fire either, and the SIEM will say nothing.

Test the configuration and the rule:

```bash
/var/ossec/bin/wazuh-analysisd -t          # configuration syntax
/var/ossec/bin/wazuh-logtest               # paste a failure line
```

**Expected:** `wazuh-logtest` shows the decoded fields, the base rule firing, and — after the sixth matching event
within the window — your rule `100420` at level 10. `wazuh-logtest` replays a single event; the composite rule may
need repeated pastes in the same session to reach the frequency. Record what you observe.

Exit the container and restart the manager:

```bash
exit
docker compose restart wazuh.manager
docker compose logs --tail=20 wazuh.manager | grep -iE 'rule|error'
```

### 5. Positive test

```bash
# On lab-ubuntu
for i in $(seq 1 6); do
  echo "$(date '+%b %e %H:%M:%S') lab-ubuntu sshd[42$i]: Failed password for invalid user labtest from 192.0.2.55 port 51$i ssh2" \
    | sudo tee -a /var/log/lab404/auth-test.log
  sleep 5
done
```

**Expected:** within a minute, an alert with `rule.id: 100420`, level 10, `data.srcip: 192.0.2.55`. Save the alert
JSON as `detections/tests/positive/alert.json`.

If nothing appears, check in this order: agent status, file monitoring, `wazuh-logtest` on the exact line, then the
manager's `alerts.log`. Do not change the threshold to "make it work".

### 6. Negative test

```bash
# Two failures, then success: the typo-and-retry pattern
for i in 1 2; do
  echo "$(date '+%b %e %H:%M:%S') lab-ubuntu sshd[43$i]: Failed password for labtest from 192.0.2.66 port 52$i ssh2" \
    | sudo tee -a /var/log/lab404/auth-test.log
  sleep 3
done
echo "$(date '+%b %e %H:%M:%S') lab-ubuntu sshd[4399]: Accepted password for labtest from 192.0.2.66 port 5299 ssh2" \
  | sudo tee -a /var/log/lab404/auth-test.log
```

**Expected:** no `100420` alert for source `192.0.2.66`. The individual failure events are still logged and visible —
the rule correctly declines to escalate them.

Record the absence in `detections/tests/negative/result.md`, with the time window you searched. "It did not fire" is
only evidence if you can show you looked.

### 7. No-data test

```bash
sudo systemctl stop wazuh-agent        # on lab-ubuntu
# generate the same six lines while the agent is down
sudo systemctl start wazuh-agent
```

Then answer, in `detections/tests/nodata/result.md`:

1. Did the rule fire? (Expected: no.)
2. How would you know the difference between "no attack" and "no data"?
3. Which control detects a silent agent: agent status, a heartbeat rule, or the absence of expected daily events?

**Expected conclusion:** a stopped agent produces no alerts, so the rule's silence is indistinguishable from safety.
The compensating control is agent-status monitoring plus a scheduled "no events from host in 24 h" check. Write that
down; it is a finding, not a failure of the lab.

### 8. Regression test after a deliberate change

Change `frequency` from 6 to 8, restart the manager, and re-run both tests:

| Test | Before (freq 6) | After (freq 8) |
| --- | --- | --- |
| 6 failures | alert | ? |
| 8 failures | alert | ? |
| 2 failures + success | none | none |

Run the 8-failure case explicitly. **Expected:** 6 no longer alerts, 8 does.

Then decide, in writing: is 8 better than 6? Argue both sides in two sentences, and state which you would ship and
what evidence would change your mind. There is no single correct threshold — there is a justified one.

### 9. Document the field mapping

`detections/mappings/field-map.md`:

| Sigma field | Wazuh field | Verified on a real event? |
| --- | --- | --- |
| `src_ip` | `data.srcip` | yes / no |
| `user` | `data.dstuser` (or the decoded equivalent) | |
| `message` | `full_log` | |
| event time | `timestamp` (manager-normalised) | |

Fill the last column by inspecting the alert JSON, not by reading documentation. Any "no" is a rule that will
silently fail once it depends on that field.

### 10. The test matrix

`detections/tests/matrix.md`:

| Test | Command/artefact | Expected | Observed | Verdict |
| --- | --- | --- | --- | --- |
| Positive | six failures, one source | alert 100420 | | |
| Negative | two failures + success | no alert | | |
| No-data | agent stopped | no alert; gap identified | | |
| Regression | frequency 8, six failures | no alert | | |

## Reflection

1. Sigma's `count(src_ip) by src_ip > 5` and Wazuh's `frequency`/`timeframe` are not the same construct. State the
   difference and one behaviour where they diverge.
2. Your negative test proves the rule stays quiet for two failures. What negative case is still untested, and what
   would you write to cover it?
3. The no-data test produced silence. Name the alert you would add to detect that silence, and its own failure mode.
4. If a colleague proposed allowlisting `192.0.2.55` because "that's our scanner", what would you ask before agreeing?

## Rubric

| Criterion | 1 — Incomplete | 3 — Competent | 5 — Proficient |
| --- | --- | --- | --- |
| Specification | Rule written without hypothesis | Hypothesis and negative case | Limits stated; conversion and its meaning explained |
| Implementation | Copied rule, unknown SID | SID observed, validated | Field mapping verified on events; semantic differences documented |
| Testing | Positive only | Positive and negative | All four, with honest reporting of the no-data gap |

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `sigma check` fails on `condition` | Aggregation syntax not supported by the spec version | Use `selection \| count(src_ip) by src_ip > 5` exactly; update sigma-cli |
| `sigma convert` unknown target | Backend plugin not installed | `sigma plugin list`, then `sigma plugin install <target>` |
| Rule never fires | Referenced base SID wrong | Find the SID with `wazuh-logtest` on the exact line |
| Rule fires on one event | `frequency` ignored because the base rule lacks `same_source_ip` context | Composite rules need the parent match; verify with logtest |
| No alerts after restart | Manager rejected the XML | `wazuh-analysisd -t`; check `ossec.log` for parse errors |
| Alert level 0 | Rule level omitted or suppressed by a parent rule | Set `level="10"` explicitly; check for `<rule id>` collisions |
| Negative test "passed" but you cannot prove it | No search window recorded | Re-run and record the exact time range queried |
